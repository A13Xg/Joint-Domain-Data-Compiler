## Implementation

`src/ui/FormValidation.ts` exports exactly the interface requested:

- `ValidationRule { validate: (value: any) => boolean; message: string }`
- `ValidationResult { isValid: boolean; errors: Record<string, string> }`
- `createValidator(rules: Record<string, ValidationRule[]>) => (values) => ValidationResult`
  - Iterates each field's rules in order and stops at the **first failing rule**
    per field, recording that rule's `message` as the field's error.
  - A rules map with no fields, or a values object where every field passes,
    yields `{ isValid: true, errors: {} }`.
- `validators` factory object:
  - `required(fieldName)` — fails on `null`/`undefined`, whitespace-only
    strings, and `NaN`; the number `0` and empty arrays/objects are treated as
    present. Message: `"${fieldName} is required"`.
  - `minValue(min)` / `maxValue(max)` — fail on non-numbers, non-finite
    values, and out-of-range numbers.
  - `positive()` — fails on non-numbers and values `<= 0`.
  - `integer()` — fails on non-numbers and non-integers (uses
    `Number.isInteger`).

`value: any` is intentional and matches the required interface exactly (rules
are matched to arbitrary form values by field name); a scoped
`/* eslint-disable @typescript-eslint/no-explicit-any */` is placed at the top
of the file with a comment explaining why, since the repo's ESLint config
otherwise bans explicit `any`.

## Test coverage (`test/form-validation.ts`)

Follows the repo's existing test-harness convention (see
`test/chart-type-validator.ts`): local `check(name, condition)` counting
failures, `console.log` per assertion, exit code reflects pass/fail.

Covers:
- Each validator individually (pass + fail cases), including edge cases:
  empty/whitespace strings, `NaN`, `0`, `Infinity`, non-number types.
- `createValidator` with a single rule per field (pass/fail).
- `createValidator` with **multiple rules on one field**, verifying the first
  failing rule wins (required → positive → integer → maxValue chain).
- `createValidator` across **multiple independent fields**, verifying errors
  are field-scoped and partial failures only report the failing field.
- `createValidator` with an empty rules map (always valid).

45/45 checks pass.

## Notes for Task 7 (TransformPanel integration)

- Rule composition order matters: put `required` first when combining with
  `positive`/`integer`/`minValue`/`maxValue`, since those numeric rules treat
  non-numbers (including `undefined`) as failing anyway, but `required` gives
  the clearest message for an empty field.
- `errors` is a flat `Record<string, string>` keyed by the same field names
  passed into `values`/`rules`, so it can be spread directly into per-field
  error message UI.
